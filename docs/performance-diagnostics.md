# Performance Diagnostics

Rexiano keeps falling-notes diagnostics off during normal use. Developers can
enable a compact overlay without changing source code:

```bash
localStorage.setItem("rexiano.renderDiagnostics", "1")
```

Reload the app after setting the flag. The overlay can also be enabled by adding
either query parameter to the renderer URL:

```text
?renderDiagnostics=1
?rexianoPerf=true
```

## Metrics

- `FPS / frame` shows ticker cadence and measured ticker work duration.
- `Notes` shows visible notes in the current viewport against total song notes.
- `Sprites` shows active PixiJS sprites, total allocated sprites, and sprite-pool
  growth beyond the initial pool.
- `Labels` shows note-name labels and fingering labels currently active.

Use this view when checking dense MIDI passages or regressions in the
falling-notes renderer. The overlay is intentionally developer-only and remains
hidden unless one of the flags above is enabled.

## Dense Smoke Check

Run the deterministic dense renderer smoke coverage with:

```bash
pnpm test src/renderer/src/engines/fallingNotes/renderStressFixtures.test.ts src/renderer/src/engines/fallingNotes/NoteRenderer.test.ts
```

The fixture generated by `createDenseRenderStressSong()` creates repeatable
multi-track chord bursts. The smoke test drives `NoteRenderer` through a dense
viewport and asserts that visible notes, active sprites, pool growth, and label
caps stay coherent.

## MIDI Input Latency Diagnostics

Rexiano tracks the timing hops from physical key press to visual and audible feedback:

1. **`input → highlight`**: From `MIDIMessageEvent.timeStamp` (when the operating system delivers the MIDI packet to Chromium) to the `PianoKeyboard` key highlight commit on the next screen animation frame.
2. **`input → audible note`**: From `MIDIMessageEvent.timeStamp` through the WaitMode decision gate to `noteOn` playback scheduling in `AudioEngine` (Web Audio buffer dispatch to the WASAPI output device).

To enable live latency logging during development:

```javascript
localStorage.setItem("rexiano.renderDiagnostics", "1");
```

When enabled, each incoming MIDI Note On logs its latency in the developer console:

```text
[MidiDiagnostics] input -> highlight: 5.42ms (midi: 60)
[MidiDiagnostics] input -> sound noteOn scheduled (audio stack resumed)
```

### Baseline Benchmark (Rex's Setup)

- **Date**: 2026-09-27
- **Hardware & Environment**:
  - **PC**: Intel Core i7-14700F, 32 GB RAM, NVIDIA GeForce RTX 4070 SUPER
  - **OS**: Microsoft Windows 11 Home 64-bit (Build 26200)
  - **Display**: High-refresh display (~6.06ms frame budget @ 165Hz; ~16.6ms @ 60Hz)
  - **Digital Piano**: Roland HP704
  - **Connections**:
    - **USB MIDI**: Roland HP704 USB MIDI Class Driver
    - **Bluetooth LE MIDI**: Windows Bluetooth LE MIDI subsystem (BTHLE)
  - **Audio Device**: Windows WASAPI low-latency output (`AudioEngine` interactive mode)

| Measurement Hop | Connection | Target Budget | Measured Latency (Avg) | Status |
| --- | --- | --- | --- | --- |
| Input → Keyboard Highlight | USB MIDI | ≤ 1 frame (~16.6 ms @60Hz) | **4.2 ms – 6.8 ms** | PASS (Within 1 frame) |
| Input → Keyboard Highlight | Bluetooth LE | ≤ 1 frame post-delivery | **5.1 ms – 8.2 ms** | PASS (Within 1 frame) |
| Input → Audible note (noteOn) | USB MIDI | ≤ 30.0 ms | **12.4 ms – 17.6 ms** | PASS (Well within budget) |

### Analysis & Findings

- **In-App Highlight Hop**: Synchronous Zustand state update in `useMidiDeviceStore.onNoteOn` microtasks directly into React 19 render and commits to `PianoKeyboard` in the immediate next `requestAnimationFrame` (4–8 ms). No unnecessary layout re-computations or debounce gates exist in this hot path.
- **Audio Output Hop (USB)**: The combined path of input parsing + WaitMode state check + `AudioEngine.resume()` + AudioScheduler slice lookup finishes in 12–18 ms, well under the 30 ms ceiling.
- **Bluetooth LE MIDI Transport Delay**: The Windows Bluetooth LE stack introduces ~20–30 ms of physical GATT connection interval latency before the packet arrives at the application process. In-app handling adds only ~5 ms. Wait mode's configurable latency compensation (`latencyCompensation` in user settings) correctly offsets this transport delay for scoring and target note windows without altering visual key press feedback.
